# Разработка Messa

1. Изучите README, SECURITY и архитектуру.
2. Создайте ветку для одного законченного сценария. Не коммитьте `.env`, базу, вложения и реальные пользовательские скриншоты.
3. Проверяйте `npm run check`, `npm test` и при изменении UI — `npm run test:e2e` на **тестовой** базе.
4. Каждая операция должна иметь границу авторизации, лимиты ввода, явную ошибку и тест на чужого пользователя.
5. Сначала сохраняйте durable-данные, потом публикуйте событие. Сетевой повтор не должен порождать дубли.
6. Все пользовательские строки экранируются в слое представления. Нельзя добавлять inline handlers, опасные URL и `innerHTML` с сырыми данными.
7. Любое изменение схемы — новая версия миграции с тестом восстановления. Нельзя править схему уже установленной базы только редактированием исходного SQL.
8. Интерактивные элементы — настоящие кнопки/поля с подписью и фокусом; проверяйте телефон, длинные сообщения, отсутствие данных, обрыв связи и reduced-motion.
9. Не рекламируйте несуществующую безопасность: TLS не является E2EE; локальный тест не является независимым аудитом; CSS-макет не является рабочим звонком.
10. В PR укажите поведение, риски и откат. Не публикуйте security-репродукции с реальными секретами в открытых Issues.

Runtime не требует npm-зависимостей. Не добавляйте пакет ради нескольких строк очевидной стандартной логики. Для сложной криптографии, напротив, запрещено изобретать собственный протокол — требуется отдельный дизайн и проверенная библиотека.
