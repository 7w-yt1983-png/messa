# Архитектура и продуктовые решения

## Цель первого релиза

Реальная переписка между независимыми аккаунтами; быстрый запуск без облачных ключей; аккуратный интерфейс и проверяемые границы безопасности. Приоритет — законченные ежедневные сценарии, а не десятки неработающих кнопок.

## Слои

- `public/app.js`: состояние приложения, координация API/событий, диалоги и навигация. Список, шапка, сообщения и композер обновляются раздельно: ввод не теряет фокус от каждого события.
- `public/view.js`: чистое экранирование/представление. Пользовательский текст никогда не становится исполняемым HTML.
- `public/api.js`: HTTP, таймауты, CSRF только в памяти, поток SSE и проверка истёкшей сессии.
- `public/demo.js`: отдельный in-memory адаптер. Те же UI-сценарии, ни одного обращения к реальному серверу. Режим явно обозначен.
- `server/app.mjs`: маршруты, авторизация, сериализация, ограничения запросов, статика.
- `server/security.mjs`: scrypt, токены, валидация, лимиты и проверка файлов.
- `server/events.mjs`: ограниченные SSE-подключения, присутствие и доставка только участникам.
- `server/db.mjs` / `schema.sql`: транзакции и версия схемы. При несовместимой более новой схеме запуск прекращается.

## Модель данных

`users` → `sessions`; `chats` ↔ `users` через `members`; `messages` → `files`, `reactions`.

- UUID используются для пользователей, чатов и файлов. Последовательный ID сообщения даёт однозначный порядок и курсор прочтения.
- Уникальный `direct_key` не даёт создать два личных чата для одной пары.
- Пара `(sender_id, client_id)` гарантирует одну запись при конкурентных повторах. Если HTTP-ответ потерян после commit, повтор с тем же ключом вернёт уже записанное сообщение.
- `last_read` движется только вперёд. Нельзя прочесть сообщение из другого чата.
- Данные сохранены до публикации события; сбой SSE не означает потерю истории.
- Удаление оставляет tombstone, чтобы клиенты не перепутали порядок. Текст/реакции/вложение удаляются, остальные метаданные сохраняются.
- Вложение сначала принадлежит только загрузившему участнику, затем становится доступно участникам после отправки. Нельзя подставить чужое вложение или прикрепить его повторно.

## Realtime и сбои

HTTP POST/PATCH/DELETE отвечает за durable-операции; SSE — за двусторонне наблюдаемое обновление интерфейса. Клиент использует стандартное переподключение EventSource и при `ready` заново запрашивает чаты/актуальную историю. Это reconciliation, а не replay всех событий: старые страницы истории можно загрузить снова.

SSE не использует URL-токены: аутентификация через cookie. Подключение проверяет срок/наличие сессии каждые 20 секунд; явный выход сразу закрывает поток. До шести потоков на аккаунт. Медленный потребитель отключается при переполнении буфера.

Ввод сохраняет черновик в текущей вкладке. Отправленное оптимистически сообщение имеет состояние «отправляется» либо «повторить». Автоматической бесконечной отправки нет. Повтор безопасен за счёт того же `clientId`. Пустое сообщение и файл больше лимита не уходят на сервер.

Прочтение отправляется только для открытого, видимого, прокрученного вниз чата, не для поисковой выдачи. Отметка в интерфейсе означает прочтение хотя бы одним другим участником.

## UI и доступность

Спокойная сине-серая палитра, CSS layers и переменные вместо множества несвязанных стилей. Light/dark/system, reduced-motion, нативные modal dialogs, фокус клавиатуры, экранные подписи, текстовые состояния ошибок/отправки. Десктоп — навигация/список/чат; мобильный — список либо один разговор, с отдельной кнопкой назад. Инспектор не сжимает узкий экран.

Текст переписки не попадает в уведомления. Шрифты, иконки и логотип локальные. Никаких счётчиков «миллионов пользователей», искусственных показателей защиты или неподключённых кнопок звонков.

## Границы и дальнейшее масштабирование

Один Node-процесс, локальная SQLite WAL, локальные вложения. Подход удобен для пилота/закрытого клуба, но синхронная SQLite и process-local события ограничивают нагрузку. Цифра одновременных пользователей не заявляется без нагрузочных измерений.

Для роста: PostgreSQL + явные миграции, транзакционный outbox, брокер событий/распределённое присутствие, объектное хранилище с проверкой файлов, распределённые rate limits, мониторинг и нагрузочное тестирование. Нельзя просто поднять второй контейнер с той же базой и назвать это кластером.
