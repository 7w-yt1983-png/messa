# Запуск, HTTPS и эксплуатация

## 1. Локально

Нужен Node.js 24.14+ (24.x). Команда `npm start` запускает приложение без установки библиотек. При старте может появляться предупреждение Node о статусе встроенного SQLite; оно не означает ошибку миграции.

```bash
cp .env.example .env
npm run check
npm test
npm start
```

Откройте `http://localhost:3000`. Для проверки реальной доставки используйте два аккаунта в двух отдельных браузерных профилях. Обычные вкладки одного профиля разделяют одну cookie и один аккаунт.

Локально регистрация открыта. База и вложения появятся в `data/`. Не заменяйте этот каталог при обновлении исходников.

## 2. Перед доступом из интернета

Нужны собственный сервер, домен с A/AAAA-записью на него и Docker Compose v2. Это отдельные ресурсы: репозиторий не покупает их и не выполняет развёртывание автоматически.

Сначала оцените ограничения в `SECURITY.md`. Для этой версии рекомендуем небольшую закрытую группу. Нет E2EE, восстановления забытых паролей, MFA, блокировки пользователей и внешнего аудита.

Создайте **на сервере**, вне Git, `.env`:

```dotenv
MESSA_DOMAIN=chat.example.com
APP_ORIGIN=https://chat.example.com
ALLOW_REGISTRATION=false
REGISTRATION_CODE=
```

Для первого создания аккаунтов временно установите `ALLOW_REGISTRATION=true`, сгенерируйте и запишите в `REGISTRATION_CODE` случайное значение длиной не менее 20 символов. Генератор:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Передавайте код только приглашённым людям по доверенному каналу. Никогда не публикуйте его в README, Issues или коммитах. После создания аккаунтов снова закройте регистрацию и пересоздайте контейнер приложения. Существующие аккаунты продолжат входить.

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
# Проверка без вывода конфигурации/секретов:
curl -fsS https://chat.example.com/healthz
```

Caddy принимает 80/443 и получает сертификат. Приложение не публикует порт 3000 наружу. SSE проходит без буферизации. Оболочка приложения read-only; писать разрешено в named volume `messa_data`. Используется непривилегированный пользователь `node`.

**Не отключайте HTTPS ради обхода ошибки запуска.** Production намеренно не запускается при HTTP или открытой регистрации без приватного кода. `APP_ORIGIN` — строго origin без пути, query и завершающего `/`.

## 3. Настройки и ограничения

- `HOST`, `PORT`: адрес внутреннего HTTP-сервера. Для локального запуска — 127.0.0.1:3000.
- `APP_ORIGIN`: единственный разрешённый origin для мутаций, обычно `https://chat.example.com`.
- `NODE_ENV=production`: Secure cookies, HSTS и закрытая по умолчанию регистрация.
- `DATA_DIR`: каталог базы/вложений, по умолчанию `./data`.
- `ALLOW_REGISTRATION`, `REGISTRATION_CODE`: правила регистрации; код не возвращается в публичном API.

Вложения: 10 МБ/файл, 200 МБ/аккаунт, 5 ГБ суммарно. Чаты: до 200 на аккаунт, группы до 32 участников. Ограничения фиксированы в `server/config.mjs` / маршрутах, меняйте их осознанно вместе с тестами и инфраструктурой.

Приложение не доверяет X-Forwarded-For. За Caddy IP-квоты общие для пользователей прокси. Для публичного запуска нужны проверенный trusted-proxy механизм и отдельная модель противодействия злоупотреблениям, а не безусловное доверие заголовку.

## 4. Бэкап — только после остановки записи

База **и** вложения должны соответствовать одному моменту. Не копируйте один SQLite-файл без WAL/вложений во время работы.

Для запуска без Docker:

1. Остановите сервер (Ctrl+C / менеджер процессов).
2. Выполните:

```bash
MESSA_BACKUP_OFFLINE=1 npm run backup -- ./backups/pre-update
```

3. Проверьте итоговый `manifest.json`, сохраните копию на другом носителе с шифрованием.
4. Снова запустите сервер.

Скрипт использует SQLite backup API, копирует вложения, сверяет размеры, SHA-256 и `integrity_check`; не перезаписывает существующую копию. Флаг — ваше подтверждение остановки сервера, не автоматический детектор процессов. `.env` и секрет приглашения в копию не включаются. Сессии, пароли в виде хешей и сообщения в копию входят.

В Docker скрипт тоже присутствует. Создайте локальный каталог `backups`, доступный UID/GID 1000, и выполните:

```bash
docker compose stop app
docker compose run --rm --no-deps -e MESSA_BACKUP_OFFLINE=1 \
  -v "$PWD/backups:/backups" app node scripts/backup.mjs /backups/pre-update
docker compose start app
```

Если резервное копирование завершилось с ошибкой, устраните причину и убедитесь, что сервер снова запущен. Защитите каталог резервных копий, не отдавайте его веб-сервером и не коммитьте.

## 5. Восстановление

На **остановленном** сервере сохраните текущий каталог данных под другим именем. Скопируйте `messa.sqlite` и `uploads/` из выбранного бэкапа в пустой `DATA_DIR`, с правами пользователя приложения. Не оставляйте старые `messa.sqlite-wal`/`messa.sqlite-shm` от другой базы.

Для Docker восстановите их в том же named volume через временный контейнер или `docker cp` в остановленный контейнер, затем проверьте владельца UID/GID 1000. Запустите приложение, проверьте `/healthz`, вход, историю **и скачивание вложения**. Проводите тестовое восстановление на отдельном окружении; ни разу не восстановленный бэкап не считается проверенной защитой.

## 6. Обновления и наблюдаемость

- Перед обновлением — полный бэкап и проверка изменений схемы. Отдельно проверяйте восстановление.
- `npm run check`, `npm test`, браузерный suite — на тестовой базе.
- Мониторинг `/healthz`, свободного диска, памяти, ошибок и корректного HTTPS.
- В логах внутренних ошибок есть request ID, тип/код ошибки; не логируются пароль или тело сообщений.
- SIGTERM/SIGINT закрывают потоки и сервер; жёсткий предел завершения — 10 секунд.
- Один Node-процесс на базу. Не масштабируйте контейнер репликами: потребуется другая архитектура.
- Обновляйте базовые образы после тестов. Docker/сертификаты/DNS надо проверять на реальном хосте; локальные browser/API тесты это не проверяют.
